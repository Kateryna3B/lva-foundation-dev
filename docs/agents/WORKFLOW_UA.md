# Регламент команди — org2

## Власники рішень
Замовник затверджує цілі, зміни вимог, витрати та приймання на своєму Windows. Головний агент об'єднує ролі архітектора, диспетчера та інтегратора: сам ставить завдання, отримує патчі, перевіряє і зводить випуск. Не перекладати перенесення коду, Git merge чи маршрутизацію на замовника.
A — дані/час; B — сховище/процеси/UI; C — незалежний QA і документація. Ролі не означають три постійні запущені процеси. Gemini — зовнішня second opinion на контрольних точках; прямий доступ не підключено. Висновки Gemini мають ACCEPT/ADAPT/REJECT/DEFER з причиною.

## Режим з урахуванням лімітів
За замовчуванням один виконавець, потім окремий QA на зафіксованому результаті. Два виконавці одночасно лише для незалежних allowlist та контрактів, коли очікуваний виграш більший за додаткове читання/інтеграцію. C може раніше підготувати критерії, але не отримує весь діалог реалізації. Не запускати агента лише для підтримання формального складу команди; не створювати дочірніх агентів без доручення інтегратора.
Фактичні лічильники витрат, якщо доступні, мають джерело/дату; інакше unknown. Кількість звернень, довжина чату й токени не є взаємозамінними метриками. Окремі чати не гарантують окремої квоти. Гарантій економії немає.

## Контекст задачі
Перед запуском: task card, точний base_commit, prompt_version, мета, versioned contract, allowlist, залежності, необхідні файли/fixtures та критерії приймання. Агент отримує мінімально достатній пакет, без повної історії чату; якщо механізм дозволяє, fork_turns=none. Головний агент сам добирає залежності, не змушує замовника вручну готувати контекст.
Контракти належать інтегратору. A/B можуть пропонувати зміни, але не вводять нову API-семантику односторонньо. B не обов'язково чекає всю реалізацію A: незалежні компоненти працюють від frozen contract.
Передавати іншому агенту фінальні рішення та важливі unresolved findings. Чернетки не переносити без потреби; абсолютна заборона cross-context небезпечна, бо приховує спільні ризики.

## Git та інтеграція
Для одночасних записів — окремі worktree/branches на одному base_commit. Гілка без окремої робочої копії не ізолює файли. У спільній копії — лише послідовний запис або явний неперетин allowlist; один власник shared core/asr/schema/release.
Вихід виконавця: patch/commit, перелік файлів, test evidence, залишкові ризики. Великий код не копіювати у відповіді, коли файл/диф доступний. Review читає diff разом із контрактом, релевантними callers і tests; сам diff не завжди достатній.
C перевіряє критерії незалежно від пояснень автора. Виконавці також пишуть релевантні тести своїх змін. Інтегратор сам читає код і відтворює критичні перевірки; чужий green test report не є остаточним доказом.
Merge послідовний; інтеграційні тести запускаються на точному candidate commit. Після зміни candidate попередня QA позначається superseded для зміненого обсягу. Unit/mocks не замінюють реальний Windows/ASR/LVA acceptance.

## Checkpoint та відновлення
PROJECT_STATE.md — компактний індекс; TASK_BOARD — статуси; ADR — архітектура; CHANGELOG — випуски; журнал — підтверджені події. Не дублювати весь журнал у PROJECT_STATE.
Зберігати checkpoint після прийнятої задачі, перед значною зміною контракту або ризиком вичерпання контексту/квоти. Нову сесію створювати за межею задачі або при втраті фокусу, а не за довільним порогом 15 повідомлень.
Якщо два виправлення не змінюють клас помилки — зупинити сліпі повтори, зібрати мінімальне відтворення та передати інтегратору. За ризику втрати даних ескалація одразу. Ліміт: записати BLOCKED_QUOTA й стан файлів; перевірити diff, незавершені процеси та uncommitted changes перед повторним дорученням.
Немає роботи у фоні між зверненнями або гарантії постійного збереження scratch. Продовжувати від збереженого Git/checkpoint-пакета.

## Хмарні інструменти розробки
GitHub рекомендований для коду, PR і CI; локальний Git вже дозволяє worktree та контроль версій. До підключення зберігати bundle/checkpoint. Публікація тільки в погоджений private remote після перевірки історії й даних.
Drive — дозволені довідкові матеріали, synthetic fixtures, перевірені ZIP/bundles. Не робоча копія Git чи live registry. Невеликі WAV fixtures для тестів краще генерувати в тесті. Важкі fixtures: hash, provenance, очікуваний результат і шлях завантаження; окремий optional acceptance, без mandatory cloud access для офлайн suite.
Docs — спільні чернетки й коментарі; затверджена версія переходить у Git ADR/contract. Sheets — лише необов'язкова проєкція задач/витрат, із owner та датою синхронізації. До GitHub Issues канонічна дошка в Git; після переходу Issues стає джерелом задач, TASK_BOARD — індекс/знімок.
Цей етап нічого не підключає до runtime Foundation і не додає cloud dependencies.
