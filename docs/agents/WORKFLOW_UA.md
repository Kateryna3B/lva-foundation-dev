# Команда агентів

## Рекомендований склад
5 ролей: головний інтегратор + A (дані/час), B (платформа/UI), C (QA/документація), Gemini (зовнішня рецензія). Зазвичай працюють 2 виконавці та 1 QA; Gemini — на контрольних точках. Не потрібен постійний агент на кожний файл.

Рівень A/B — сильна модель програмування з глибоким reasoning для часової шкали/сховища. C — сильна аналітика, коротші режими для механічної документації. Інтегратор — найретельніший аналіз для контрактів і приймання. Для Gemini обрати доступний режим поглибленого аналізу; конкретну назву моделі фіксувати у звіті фактичного запуску. Це профілі задач, не неперевірений рейтинг моделей. Не змінювати моделі лише задля різноманітності.

## Розподіл
A/B: окремі worktree на одному base_commit. C готує незалежні критерії, потім перевіряє конкретні commits. Інтегратор володіє schemas/release та розподіляє core/asr за одним writer. Схема звіту може проєктуватися паралельно; інтеграція залежить від прийнятого time map.

## Цикл
1. Інтегратор заповнює TASK_CARD, фіксує contracts і base.
2. A/B працюють у allowlist, повідомляють про блокери інтегратору.
3. C відтворює ключові сценарії й записує findings.
4. Інтегратор читає diff і сам перевіряє критичні твердження. Послідовно об’єднує зміни; вирішує конфлікти.
5. На інтегрованому commit запускає потрібні перевірки, оновлює docs.
6. Gemini рецензує snapshot контрольної точки. Висновки отримують ACCEPT/ADAPT/REJECT/DEFER з причиною.
7. Інтегратор готує один release candidate та локальний Windows-чеклист. Приймання аудіо/Windows виконується там, де вони доступні.

## Gemini: фактичний маршрут
Автоматизований доступ до Gemini в цій роботі не підключено; Gemini ще не викликався. Користувач може передати промпт 04 разом із дозволеним snapshot/diff і повернути висновок. Для організаційної рецензії достатньо docs і START_HERE; для аудиту коду потрібні відповідні source-файли. Не додавати автоматично всю справу. Майбутня API-інтеграція — окрема задача з вибором доступу/витрат, не частина org1.

## Докази та економія
Менше звернень користувача не означає менше токенів. Після двох пакетів порівняти: час до приймання, витрати за доступними лічильниками, кількість звернень, повторних переробок, регресій і конфліктів. Скорочувати паралельність, якщо інтеграція з’їдає виграш. Не мати паралельно двох великих ASR-процесів на тестовому ноутбуці лише заради кількості агентів.

## Удосконалення промптів
Кожен task містить prompt_version. За дефектом визначити: код, прогалину контракту, недостатній контекст чи невиконану інструкцію. Оновити лише релевантний пункт, додати приклад/регресійний критерій, збільшити версію промпта, записати причину в PROMPT_CHANGELOG. Інтегратор перевіряє наслідки. Помилка одного агента не стає універсальним правилом для всіх без підстав.

## Поточний стан
Два агенти виконали read-only організаційні ревізії. Ролі A/B/C нижче підготовлені для майбутніх задач, не є постійно запущеними сервісами. Функціональні задачі S1 у org1 не виконувалися.
