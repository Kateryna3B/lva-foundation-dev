# Експлуатація та відновлення

## Резервування даних
Завершіть активний ASR. «Резервувати» створює backup_UUID поза робочим каталогом. «Перевірити копію» або Verify_Backup.py перевіряє COMPLETE.json і файли. Успішна перевірка hash не замінює пробного відновлення.

## Пробне відновлення
Скопіюйте вміст завершеної копії в новий порожній локальний каталог, відкрийте його програмою, виконайте «Відновити», потім «Перевірити». Перевірте справи й доступність результатів. Не підміняйте живу БД. Якщо повідомлено конфлікт hash/частковий файл — зберігайте журнал і матеріали для діагностики; автоматичне видалення не передбачено.

## Зупинка/повтор
Зупинка ASR зберігає завершені канали як checkpoints; поточний канал може виконуватися заново. Пошкоджений checkpoint блокується. Штатна копія переносить зареєстровані артефакти, але не є гарантією перенесення незавершених _asr_jobs, venv або моделей.

## Відкат коду
Git tag/bundle повертає код. Він НЕ повертає БД/аудіо. Для поточної org1 код функціонально тотожний 0.2.4. Після майбутніх міграцій запуск старої програми проти нової БД без перевіреної сумісності заборонений; потрібна сумісна окрема копія даних.

## Діагностика
Зберігайте версію програми, run_id, текст помилки, етап/PID, шлях журналу, scope, статуси каналів, timings_seconds. Manifest містить реквізити справи; перед передачею зовнішньому рецензенту використовуйте лише дозволений тестовий комплект. Не редагуйте manifest для зміни станів.

## Наявні межі
Один writer на реєстр, локальний диск, NAS/планові копії/ACL/шифрування/ретенція ще не завершені. Робочий SQLite не переносити в синхронізовану хмарну папку як спосіб резервування активної БД. Окрема папка обміну містить копії дозволених матеріалів.
